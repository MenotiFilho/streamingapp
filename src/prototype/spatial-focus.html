Prototype · throwaway · issue #51

Spatial focus and D-pad navigation

Today focus is one flat line: next control in DOM order, wrapping. This prototype replaces that with a spatial model and puts it under a real Home grid and nav rail, so you can feel whether it is right. Click the buttons, use the arrow keys, plug in a pad — all three drive the same model.

The question. Is a spatial-focus model — movement by geometry inside a region, a defined crossing between stacked regions, a region stack for Back — the right input model for the window, and does it hold up at the edges (a row's end, a short row, a vanished control, a caret in a text field)?

Arrows move · Enter / Space is OK (the control's own click — nothing here re-implements activation) · Escape or Backspace is Back. A focused card is the one with the ivory ring and crimson halo.

    Guided walkthroughs

      The model, in words

      One snapshot, one decision

      Nothing in the model keeps a running position. Each move hands the pure module a layout — every region with its rectangle, its parent, and the rectangles of its items — plus where focus is and which rule set applies. It returns where focus goes and why. The page around it only measures boxes, paints the ring, and scrolls.

      The decision, in order

      • Inside the region, by geometry. The nearest rect in that direction wins: lined-up candidates first (a card below, not below-and-to-the-side), then the smallest sideways gap, then the shortest step, then the closest centre across. This is what makes Down land on the card below and Right walk a strip.
      • Out to a sibling region — but only one that overlaps us across the way. That single rule is what stops Right at the end of a short row falling diagonally into the next row down, while still letting Left reach the rail (which spans the height) and Down reach the row below (which spans the width).
      • Entering a region: the item whose own span covers the middle of what you came from, else the nearest one, else the region's remembered card, else its head — and the head outright when the thing you came from is wider than the whole region, which is why Down from the hero or from the search box lands on the row's first card. The rail is the exception that proves the rule: Right from the rail's Library icon enters at whatever card sits at that height.
      • The edges are walls with one rule each: a row's end, the rail's end, and Up off the top of the content. Each can stop, wrap, or (Up) hand you to the rail — that is what the switch panel is for.

      The region stack

      Back pops one level and restores that level's focus exactly — including the level below it, untouched. Screens switched from the rail are not pushed: the rail is persistent, so Back on a screen returns to Home rather than walking back through every icon you visited. That is the nav shell's decision (#52), not this prototype's; it is here so the stack has something real to push and pop.

      The same behaviour in the companion's page (no React)

      The companion is one hand-written file with no build step (ADR-0017), so nothing is imported from src/. What carries over is the shape, not the code:

      • The pure functions are inlined. The geometry functions above are a few dozen lines of plain arithmetic with no DOM in them; they paste into the companion's single <script> unchanged, because getBoundingClientRect feeds them the same rectangles on either side.
      • The layout is described in markup. The window would use a data-region / data-focusable convention; the companion gets the same attributes by hand on its three surfaces (browse, mini-strip, remote), and the same "read the DOM, decide, paint" pass runs there.
      • Only the key column of the intent table. The companion is served over plain HTTP on the LAN — an insecure origin, where getGamepads() returns nothing (research #49). So it dispatches move / back from keydown and drops the pad column entirely. Its existing single keydown listener for Escape becomes the dispatch point.
      • Shallow tree, same rules. The companion has no rail and no stacked rows, so its region tree is two levels deep — and the walls (a sheet's edge) are where its Back goes, not an arrow.
      • One copy to keep honest. The intent table is mirrored by hand, the way the companion already mirrors pure decisions from src/*.ts; a test asserting the companion's copy equals the window's (the precedent is host-wire::remote asserting the companion's capability list equals Action::SPELLINGS) keeps the two from drifting.
      • The pad column is the window's alone, and only on Windows. The research found the Gamepad API off by default in WebKitGTK, so on Linux — the dev environment — the window is keyboard-only until someone needs a pad there, which would take a Rust-side reader (gilrs) publishing these same intents. The companion is keyboard and touch on every platform, and that is not a gap: its page is served over plain HTTP, an insecure origin, where getGamepads() returns nothing at all.

      What is deliberately not here

      • Visuals: the tokens and component kit are ticket #50's answer, not this one.
      • The media intents (play/pause, seek, stop, menu) from the research table — this prototype only decides the focus model, so it carries move / activate / back.
      • Tests: it is a prototype. The pure module is the part worth lifting, and it lifts tested (the repo's TDD norm), not here.
